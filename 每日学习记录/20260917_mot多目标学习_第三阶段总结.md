## 二、开工前的排查：三个必须先修的 Bug

在动手整合之前先做了一轮代码审查与边界测试。

**经验教训：整合之前必须先验证零件。** 否则组装完成后出现黑屏或 ID 跳变，
会误以为是整合逻辑写错，在错误的地方排查很久。

### Bug 1（致命）：`tracker/association.py` 空轨迹分支返回错误结果

原代码：

```python
    #没有轨迹时
    if len(tracks)==0:
        return(
            [],
            [],
            list(range(len(tracks)))
        )
```

`len(tracks)` 应为 `len(detections)`。此处 `tracks` 已经是空列表，
`list(range(0))` 恒等于 `[]`，因此**第一帧返回的"未匹配检测"永远为空**。

后果链条：

```text
未匹配检测 = []
      ↓
第⑤步"未匹配检测 → 创建新轨迹"拿不到任何检测
      ↓
第一帧建不起轨迹
      ↓
之后每一帧都建不起轨迹
      ↓
追踪器一个框都不会输出（黑屏）
```

实测验证（2 个检测、0 条轨迹）：

```text
matches: []   unmatched_dets: []   unmatched_tracks: []
预期:         unmatched_dets: [0, 1]
```

修正：

```python
    #没有轨迹时：所有检测都未匹配，交由上层创建新轨迹
    if len(tracks)==0:
        return(
            [],
            list(range(len(detections))),
            []
        )
```

### Bug 2（致命）：`KalmanTracker` 缺少误差协方差初始化

`cv2.KalmanFilter(4,2)` 的 `errorCovPost` **默认全为 0**，原代码只设置了
`processNoiseCov=0.03` 与 `measurementNoiseCov=1`。

这一点修正了第二阶段笔记中的归因偏差：

> 第二阶段记录把预测滞后（100.00 → 100.29 → 102.45 → 110.02）解释为
> "初始化 vx=0"，**只对了一半，主因是误差协方差初值为 0**。

详见第三节的增益实验。

### Bug 3（次要）：`SimpleTracker` 的两个缺陷

SORT 不再使用 `SimpleTracker`，但作为对照基线仍有参考价值：

```text
缺陷1：matched 列表收集后从未被使用，贪心匹配缺少唯一性约束
       实测：两个高度重叠的检测框 → 同一 track 被连续更新两次（age=3）
       两个检测只拿到一个 ID

缺陷2：mark_missed() 从未被调用
       实测：目标离开画面后仍留在 tracks 中（age=1, missed=0）
       第二阶段专门新增的 missed / max_age 机制并未接入 tracker.py
```

## 三、核心实验：卡尔曼增益为什么这么小

这是本阶段最有价值的一个实验，直接解释了一个反直觉现象。

### 实验记录

- **目标**：验证 `errorCovPost` 初值与过程噪声 Q 对卡尔曼预测滞后的影响
- **数据集**：合成轨迹（无真实数据集），匀速直线运动，x1 每帧 +10
  （110 → 120 → 130 → 140），目标框 [x1, 100, x1+100, 300]
- **环境**：Python 3.10.20 + OpenCV 5.0.0 + NumPy 2.2.6 + SciPy 1.15.3
- **硬件**：RTX 3060 Laptop 6GB（本实验为纯 CPU 数值计算，不使用 GPU）
- **超参数**：
  - 状态 `[cx, cy, vx, vy]`，测量 `[cx, cy]`
  - 过程噪声 Q：`0.03` → `0.1`
  - 测量噪声 R：`1`（不变）
  - 误差协方差 `errorCovPost`：`0`（OpenCV 默认）→ `10I`
  - 状态转移矩阵 A：匀速模型（位置 += 速度）
- **命令**：

```bash
conda run -n yolov8 python test_kalman.py
```

- **产物路径**：控制台输出（`test_kalman.py`）

### 增益计算

用 A、H、R 直接算稳态卡尔曼增益 K = P_prior·Hᵀ·(H·P_prior·Hᵀ + R)⁻¹：

| 配置 | 位置增益 K[0,0] | 速度增益 K[2,0] |
|---|---|---|
| 原：Q=0.03，`errorCovPost=0` | **0.0291** | **0.0** |
| 新：Q=0.1，`errorCovPost=10I` | **0.9526** | **0.4739** |

**位置增益相差 32.7 倍，而原配置的速度增益精确等于 0。**

### 预测精度对比

| 帧 | 检测 x1 | 修改前预测 | 修改后预测 | 修改后误差 |
|---|---|---|---|---|
| 1 | 110 | 100.00 | 100.00 | — |
| 2 | 120 | 100.29 | **114.27** | 5.73 |
| 3 | 130 | 102.45 | **128.06** | 1.94 |
| 4 | 140 | 110.02 | **139.18** | **0.82** |

### 结论

```text
修改前：预测器"学"了 4 帧仍停在 110，滞后真实位置 30px
修改后：第 4 帧预测 139.18 vs 真实 140，误差仅 0.82px
```

**机理**：`errorCovPost` 表示"当前对状态估计的不确定度"。初值为 0 意味着
滤波器认为自己的初始估计完全可信，于是卡尔曼增益被压到接近 0，
几乎不采信 YOLO 的检测结果。速度分量增益精确为 0，说明**速度状态完全学不动**，
这正是"预测严重滞后、要很多帧才估计出速度"的根本原因。

初值设为 `10I` 表示"一开始对目标状态完全不确定"，滤波器因此愿意大量采信检测，
一帧内就完成收敛。

**这一步对后续追踪精度至关重要**：SORT 依赖预测框与检测框计算 IoU，
预测不准会直接导致关联失败、ID 跳变。

## 四、Track 改造：让轨迹自带滤波器

核心设计决策：**把 KalmanTracker 作为 Track 的成员**，
`predict()` 把预测结果写回 `self.bbox`。

```text
这样 association.py 里计算 IoU 用的 track.bbox
自然就是"预测框"，而不是"上一帧的检测框"
```

正好对应七步流程中的第①②步，无需改动 `association.py` 的接口。

新增方法：

```text
predict()            ① 用 Kalman 预测，结果写回 bbox
update(bbox)         ④ 匹配成功：kalman.update() + bbox 以检测为准
mark_missed()        ⑥ 未匹配：missed += 1
is_deleted(max_age)  ⑦ 判断是否删除
```

注意 `is_deleted()` 使用 `>` 而不是 `>=`：`max_age` 表示"最多容忍连续丢失多少帧"。

## 五、SortTracker：七步整合

新建 `tracker/sort_tracker.py`，完整实现原定流程：

```text
① Track 进行 Kalman 预测
② 使用预测 bbox 与 YOLO 检测 bbox 计算 IoU
③ Hungarian Algorithm 完成匹配
④ 匹配成功：Kalman update
⑤ 未匹配 Detection：创建新 Track
⑥ 未匹配 Track：missed += 1
⑦ missed 超过 max_age：删除 Track
```

### 实现顺序上的一个关键陷阱

**第⑥步（mark_missed）必须放在第⑤步（新建轨迹）之前。**

原因：`unmatched_tracks` 里存的是**下标**，而第⑤步会向 `self.tracks` 追加元素。

```text
正确顺序：先用下标操作（④⑥） → 再改列表长度（⑤） → 最后清理（⑦）
```

当前顺序即使写反也不会越界（下标都小于原长度），但一旦将来改为把新轨迹
插入列表前部，就会**静默地标错轨迹**。养成"先用下标、后改长度"的习惯。

## 六、测试结果：四个场景全部通过

`test_sort_tracker.py` 使用合成轨迹测试，不依赖视频与 GPU，几秒跑完。

### 测试1：ID 连续保持

```text
Frame 1  检测:2  轨迹ID:[1, 2]
Frame 2  检测:2  轨迹ID:[1, 2]
Frame 3  检测:2  轨迹ID:[1, 2]
Frame 4  检测:2  轨迹ID:[1, 2]
Frame 5  检测:2  轨迹ID:[1, 2]
```

### 测试2：短暂遮挡后恢复 ID（SORT 的核心价值）

```text
目标2丢失第1帧   ID:2  age:1  missed:1
目标2丢失第2帧   ID:2  age:1  missed:2
目标2重新出现    ID:2  age:2  missed:0    ← 仍然是 ID 2，没有变成 ID 3
```

**这是 SORT 相对 SimpleTracker 最关键的能力**：目标消失两帧后重新出现，
靠**卡尔曼预测框**把它匹配回原 ID。

如果 IoU 仍然用"上一帧检测框"计算，目标移动后 IoU 会掉到阈值以下，
只能新建 ID，身份就丢了。

### 测试3：长时间丢失后删除轨迹（max_age=3）

```text
第3帧无目标2  轨迹ID:[1, 2]
第4帧无目标2  轨迹ID:[1]        ← missed 超过 3，被删除
```

### 测试4：新目标分配新 ID

```text
Frame 1  轨迹ID: [1]
Frame 2  轨迹ID: [1, 2]        ← 老目标保持 ID 1，新目标拿到 ID 2
```

### 补充边界测试：所有目标离开画面

真实视频必然出现 `detections = []` 而 `tracks` 非空的情况。

```text
(2,0) 空矩阵 → linear_sum_assignment 返回 ([], [])，不报错
(0,2) 空矩阵 → 同样不报错
SortTracker 收到空检测 → unmatched_tracks 正确返回全部轨迹
```

结论：当前 SciPy 版本下空矩阵安全，无需特殊处理。

## 七、踩坑记录

```text
坑1：整合前未验证零件
      association.py 的空轨迹分支错误会让整个追踪器静默失效
      → 教训：动手整合前，先为每个零件写边界测试

坑2：把卡尔曼预测滞后归因于"初始化 vx=0"
      真正主因是 errorCovPost 默认全 0 导致增益趋近 0
      → 教训：现象背后的机理要用数值验证，不能凭直觉归因

坑3：混淆"预测框"与"上一帧检测框"
      预测框参与 IoU 才能实现遮挡后 ID 恢复
      → 教训：SORT 中 Track.bbox 的语义必须是"预测位置"

坑4：误以为 linear_sum_assignment 对空矩阵会报错
      实测不报错
      → 教训：边界行为要实测，不要凭猜测加防御代码
```

## 八、SimpleTracker 与 SortTracker 对比

| 维度 | SimpleTracker | SortTracker |
|---|---|---|
| 位置来源 | 上一帧检测框 | Kalman 预测框 |
| 匹配方式 | 贪心最大 IoU | 匈牙利全局最优 |
| 遮挡处理 | 无法处理，ID 丢失 | 预测框续命，ID 保持 |
| 轨迹删除 | 无（轨迹永久残留） | missed > max_age 删除 |
| 匹配唯一性 | 无约束（可一拖多） | 匈牙利保证一一对应 |
| 对应论文 | Tracking by Detection 基础 | SORT 经典结构 |

## 十、下一步：DeepSORT

SORT 的短板已经清晰可见：

```text
目标离开画面时间 > max_age
        ↓
轨迹被删除
        ↓
目标回来时只能分配新 ID
        ↓
身份丢失（ID Switch）
```

根本原因：**SORT 只使用运动信息（IoU），完全没有外观信息**。

DeepSORT 的改进：

```text
SORT      = 运动信息（IoU）
DeepSORT  = 运动信息（IoU / Mahalanobis 距离）
          + 外观信息（ReID 特征）
          ↓
          级联匹配（Cascade Matching）
```

需要学习的新内容：

```text
① ReID 特征提取网络（外观描述子）
② 余弦距离 / 马氏距离度量
③ 级联匹配策略
④ 特征库（gallery）更新
⑤ 匹配代价融合（运动 + 外观）
```

此外，本阶段遗留的两个可打磨点：

```text
① Track.update() 中 self.bbox = bbox 用检测框覆盖了预测框
   严格按 SORT 论文，应保留卡尔曼修正后的状态（correct 后的 statePost）
   区别：用检测框会引入 YOLO 抖动，用卡尔曼输出更平滑
   → 这是"观测 vs 估计"的经典权衡，值得亲手对比效果

② 状态维度简化为 [cx, cy, vx, vy]，没有尺度状态
   SORT 原文用 [x, y, s, r, vx, vy, vs]（s=面积, r=宽高比）
   目标远近变化时框大小不会自适应
```
